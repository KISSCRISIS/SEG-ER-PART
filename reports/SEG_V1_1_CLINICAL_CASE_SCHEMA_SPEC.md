# SEG v1.1 Clinical Case Schema Specification

**Phase:** SEG Phase 7.3 — Controlled v1.1 Profile Implementation Readiness  
**Mode:** `READ_ONLY IMPLEMENTATION DESIGN REVIEW`  
**Contract status:** `EXECUTABLE CONTRACT DRAFT — NOT IMPLEMENTED`  
**Profile:** `SEG_CONTENT_RECORD_V1_1`

## 1. Contract purpose

This document specifies the proposed v1.1 type-specific contract for `content_type = clinical_case`. It is an implementation blueprint, not an executable JSON Schema file and not a production record. The contract extends the preserved v1.0 shared envelope and adds a closed `content` object for Clinical Case fields.[1] [2]

A `clinical_case` is a governed, source-traceable educational case used for structured learning and clinical reasoning review. It is not automatically a Lesson, Question Bank item, protocol, patient record, or competency record.[2]

## 2. Placement and envelope

The future v1.1 record must preserve the v1.0 root envelope: `record_id`, `title`, `content_type`, `language`, `source`, `version`, root `references`, `rights`, `taxonomy`, `medical_review`, and `audit`. The v1.1 `content_type` value must equal `clinical_case` and the type-specific payload must be located at `content`.

The root `references` array remains the canonical manifest traceability envelope. The type-specific `content.references` field is the Case-level list of supporting reference links. Each Case-level link must resolve to or be traceable through a root reference entry; it must not replace the required root envelope.

## 3. Type-specific contract

The future `content` object is closed-world and contains the following required property names. Each property is a **source-linked content section** unless a scalar or link type is specified. A section object must preserve an explicit state of `present`, `absent`, or `unresolved`; an absent source section is represented as absent/unresolved metadata, not as invented prose.

| Path | Contract type | Required constraint |
|---|---|---|
| `content.case_type` | Source-supported scalar string | Required; non-empty when present. Must be explicit in the source or supplied by a separately attributable governed decision. |
| `content.presentation` | Source-linked section | Required property. When present, preserve source wording or a traceable derived/original representation with locator and origin metadata. |
| `content.history` | Source-linked section | Required property slot. If the source has no history section, record the absence/unresolved state; do not invent history. |
| `content.examination` | Source-linked section | Required property slot. Preserve examination and vital-sign findings only when supplied; do not create findings or values. |
| `content.investigations` | Source-linked section or ordered structured list | Required property slot. Preserve supplied tests, bedside tools, and results; do not add investigations or results. |
| `content.assessment` | Source-linked section | Required property slot. Structural presence does not constitute clinical approval. |
| `content.differential` | Source-linked section or ordered list | Required property slot. Must be source-supported or separately attributable to clinical/relevant review; schema design does not generate diagnoses. |
| `content.management` | Source-linked section or ordered structured list | Required property slot. Preserve source-supported management; do not create a protocol, dose, threshold, or patient-specific instruction. |
| `content.clinical_reasoning` | Source-linked section | Required property slot. Origin must distinguish source-verbatim, source-derived, and SEG-original educational content. |
| `content.references` | Array of case-level reference links | Required; each link must identify a root `references` entry or an explicitly governed supporting reference and retain a locator when available. |

## 4. Source-linked section semantics

The implementation contract should use one shared closed `source_section` definition for the section-valued fields. Its recommended semantic properties are:

| Property | Required behavior |
|---|---|
| `state` | Required enum: `present`, `absent`, or `unresolved`. |
| `origin` | Required when `state = present`: `source_verbatim`, `source_derived`, or `seg_original`. |
| `value` | Required when `state = present`; accepts the section’s scalar, ordered-list, or structured content representation under the future payload serializer. No medical content is generated by the schema. |
| `source_locator` | Required for `source_verbatim` and `source_derived` when source evidence is available; absence remains a traceability blocker, not an invitation to infer. |
| `review_note` | Optional governance note for unresolved or ambiguous structure; it is not a clinical decision field. |

The exact JSON serialization of `source_section.value` must be fixed in the separately authorized executable schema artifact. The semantic contract is fixed here to prevent loss of provenance and to distinguish literal source material from SEG-authored original educational content.[2] [3]

## 5. Validation rules

The v1.1 validator must apply the preserved root-envelope rules before evaluating Case-specific fields. It must then enforce the following:

1. `content_type` must be exactly `clinical_case` under explicit v1.1 profile selection.
2. All ten type-specific property names must be present in the `content` object.
3. No unknown properties may be accepted inside `content` or a `source_section` object.
4. `case_type` must not be inferred from a file name, directory, title, topic, or framework name.
5. A section marked `absent` or `unresolved` must not be silently converted into an empty, guessed, or synthesized medical section.
6. `content.references` must preserve traceability to the root reference envelope and must not be used to bypass exact locators.
7. `origin = source_verbatim` or any literal source display remains subject to the separate Rights Gate.
8. `origin = seg_original` does not remove the requirement for clinical/relevant review, taxonomy, audit, or approval gates.
9. The Internship track and `02_Internship` pathway must not be assigned by the validator from a path or title; explicit track evidence must remain separate.
10. A structural `approved` value is observed metadata only. The validator does not grant clinical approval, activation, publication, or learner exposure.[3]

## 6. Explicit exclusions

The contract must enforce the following semantic exclusions:

| Exclusion | Required interpretation |
|---|---|
| Patient record | `clinical_case` must not contain or represent an identifiable patient chart, encounter record, real-time clinical documentation, or patient-specific care decision. |
| Clinical protocol | `clinical_case` must not be treated as a fixed order set, operational protocol, dose protocol, resuscitation algorithm, or treatment authorization. |
| Competency approval | `clinical_case` must not be treated as a learner competency result, OSCE outcome, supervisor sign-off, procedure authorization, or credential. |
| Automatic Question Bank conversion | Embedded assessment questions remain Case sections unless separately sourced and governed as Question Bank items. |
| Automatic activation | Schema validity, profile adoption, and medical-owner authority do not activate or publish the Case. |

> **`clinical_case` ≠ patient record; `clinical_case` ≠ protocol; `clinical_case` ≠ competency approval.**

## 7. Governance, rights, and track requirements

Every Case must preserve source ID, source location, source version, checksum, root references, rights object, taxonomy ID/version, observed medical-review state, and append-only audit events. The required lifecycle remains **Source → Version → Governance Record → Clinical Review → Approval → Activation**.[3]

Rights review remains independent. Literal text, PDF, image, scanned figure, question-bank, or book-text display is blocked until the relevant Rights Gate is separately evidenced. A Reference Framework relationship can support traceability but cannot authorize display.

Clinical/relevant review remains independent of schema validation. The architecture does not invent a reviewer, decision, date, diagnosis, differential, treatment, dose, or safety claim.

## 8. Implementation handoff conditions

The contract is ready to be translated into the separately authorized v1.1 executable schema only after the implementation owner confirms the exact `source_section.value` serialization, profile artifact identity, validator behavior, and test fixtures. No production record may be generated as part of that translation. Any pilot must be read-only, reversible, source-preserving, and explicitly scoped.
